## 1. 需求与目标

### 1.1 要解决的问题

量化因子开发的现状是：研究员有一个想法或读到一篇研报，接下来要花大量时间在**非研究性劳动**上 —— 翻 Wind 数据字典找字段、确认字段口径、写取数 SQL、对齐日期、处理复权和停牌、写公式、排查未来函数、反复调试。真正的研究判断可能只占其中一小部分。

平台要做的是把这段路径自动化，同时**不牺牲正确性**：

```text
自然语言研究想法  ┐
                  ├→ 结构化因子定义 → 歧义澄清 → 字段发现与确认
中英文卖方研报    ┘                                    │
                                                       ↓
              可追溯的因子结果 ← 三层校验 ← 隔离执行 ← 确定性取数计划
```

### 1.2 两个入口，一条主流程

**自然语言入口**：用户填写研究信封（资产类型、股票池、起止日期、频率）+ 一段自然语言想法。

**研报入口**：上传 PDF，系统提取带页码证据的文本，抽取因子定义。

两个入口在"因子定义草案"这一点汇合，**之后共用完全相同的主流程**。研报入口不是第二套工作流，只是第二个数据来源。

### 1.3 交付分级与能力边界

| 级别 | 范围 | 口径 |
|---|---|---|
| **P0** | 自然语言 → 真实 Wind 数据 → 完整闭环 | 稳定、可重复 |
| **P1** | 中英文**文本型** PDF 研报入口 | 真实可运行原型 |
| **P2** | OCR、自动修复、因子检验、因子库、多因子、指数、权限、部署 | 真实可运行原型 |

**明确不承诺的部分**（写在这里是为了避免验收时预期不一致）：

- 任意 PDF 版式；图片公式、复杂数学排版、扫描件只做正文提示 + 人工确认（详见 §10.1）
- 任意资产类别；首期只做日频 A 股
- 任意公式；只支持已登记算子构成的表达式
- 分布式回测、高可用部署、企业级 SSO
- 实盘交易；指数模块止于成分与权重导出

### 1.4 项目约束

| 约束 | 内容 |
|---|---|
| 优先级 | **核心闭环的正确性与安全性第一**。进度压力下按既定顺序砍功能，不砍确认环节、真实数据、点时处理和执行隔离 |
| 范围 | 日频 A 股、中小规模研究区间、线性多因子组合，**不含实盘交易** |
| 资源 | Wind 数据权限、模型接口与预算提前落实 |
| 人力 | 1 名全职开发者，1 个月。**无专职研究人员全程参与**：由开发者完成口径整理、证据生成和初步核验，关键指标及最终验收由带教老师抽样确认（详见 §14） |

## 2. 设计思路

### 2.1 核心命题：程序主导，模型辅助

**这不是一个自由代码生成器。** 这是整个方案最重要的取舍，它决定了后面所有模块的形态。

大模型擅长把模糊的自然语言映射成结构化意图，但不擅长保证一致性、可复现性和安全性。因此职责这样切分：

| 职责 | 归属 |
|---|---|
| 语义理解、候选建议、自然语言解释 | **大模型** |
| 会话状态、版本、并发控制 | 程序 |
| 结构校验、变量绑定、复杂度限制 | 程序 |
| 字段真实性与业务口径 | 程序 + 人工确认 |
| 取数计划与查询构造 | 程序 |
| 公式求值与预处理 | 程序 |
| 安全执行与资源限制 | 程序 |
| 结果校验 | 程序 |

模型的输出**永远是数据，不是指令，也不是可执行代码**。

### 2.2 单一事实来源原则

系统里每一个关键概念**只能有一个权威表示**，其余都是它的投影。这条原则解决了评审指出的最严重的问题类别。

| 概念 | 唯一事实来源 | 投影 |
|---|---|---|
| 因子公式 | `formula_ast` | 后端确定性渲染的 `canonical_formula`（用户确认的正式公式）、模型写的自然语言解释（仅展示） |
| 预处理 | 有序 `preprocessing_pipeline` | 界面上的步骤列表 |
| 会话状态 | 不可变事件日志 | 折叠出的快照 |
| 执行内容 | 签名后的 `manifest` | 供用户审阅/导出的 `factor.py` |
| 字段口径 | 口径登记表 | 澄清卡候选项、校验阈值 |

**反例（本版已修正）**：原设计让模型同时产出 `formula_text` 和 `formula_ast`，两者都被当作正式公式。这会造成"用户确认了界面上的公式 A，系统实际执行的是 AST 表达的公式 B" —— 用户确认因此失去意义。修正方式见 §5.2。

### 2.3 人在回路：确认点设在哪里

自动化不等于无人参与。确认点设在**猜错代价最高**的地方：

| 确认点 | 为什么必须人来定 |
|---|---|
| 阻塞性歧义 | "盈利质量"用 ROE 还是 CFO/净利润，是两个完全不同的因子 |
| 因子公式 | 用户确认的必须是系统实际要执行的那个公式 |
| 字段与口径 | 字段名相似不等于业务含义相同 |
| 修复方案 | 自动修复只提出建议，执行前必须重新确认 |

反过来，有合理默认值、猜错代价可控的选择（如调仓频率）做成**非阻塞提示**，显式展示但不打断流程。

### 2.4 可复现优先于可运行

"跑出来了"和"能证明这个结果是怎么来的"是两回事。Wind 财务数据会被修订，同一份程序在不同时间跑出的结果可能不同。因此每次执行都要记录**完整的复现坐标**：输入数据哈希、查询时点、来源表与字段、数据区间、字段元数据版本、口径定义版本（详见 §9）。

### 2.5 失败是一等公民

因子开发过程中失败是常态：字段找错、窗口写反、财务数据缺失、区间无数据。设计上：

- 错误必须**分类**（输入 / 字段 / 空数据 / 时间口径 / 公式 / 资源 / 基础设施）
- 失败**保留现场**（原阶段、输入工件、错误证据），不回滚到起点
- 只有参数和公式类错误允许模型提出修订，**最多两轮**，每轮产生新版本并重新确认
- "样本区间无数据"不等于"字段无效"，必须区分（详见 §6.4）

## 3. 总体框架

### 3.1 分层架构

```text
┌───────────────────────────────────────────────────────────────┐
│                      React 工作台（浏览器）                     │
│        只渲染后端状态；SSE 接收进度；所有确认携带版本号          │
└──────────────────────────┬────────────────────────────────────┘
                           │ HTTP + SSE
┌──────────────────────────▼────────────────────────────────────┐
│                  FastAPI 模块化单体（受信任区）                 │
│                                                                │
│   编排层    唯一状态机、版本控制、事件日志、级联失效            │
│   语义层    解析、澄清、公式渲染与校验、预处理流水线、时间口径   │
│   发现层    元数据目录、字段检索、Schema 验证、样本验证、规划    │
│   执行层    manifest 构建与签名、任务入队、取数                 │
│   校验层    数据 / 公式 / 结果三层校验                         │
│   研报层    PDF 解析、OCR、证据定位、抽取                      │
│   模型层    Provider 协议、路由、结构化输出、数据合规过滤        │
│                                                                │
│   持有：Wind 凭据、模型密钥、元数据库写权限                     │
└────────┬──────────────────────────────────┬───────────────────┘
         │ 中间 Parquet + manifest           │ 参数化只读 SQL
┌────────▼────────────────┐    ┌────────────▼───────────────────┐
│   文件任务队列           │    │        Wind MySQL 副本          │
│   租约 / 幂等 / 取消     │    │   只读账号，六种受控查询形状     │
└────────┬────────────────┘    └────────────────────────────────┘
┌────────▼──────────────────────────────────────────────────────┐
│              Worker（隔离执行面，无网络、无密钥）               │
│   校验并执行 manifest → 公式求值 + 预处理 → 结果 Parquet        │
└───────────────────────────────────────────────────────────────┘
```

### 3.2 模块职责边界

系统的可维护性靠职责边界保证，四条硬规则：

- **契约层不含 I/O** —— 它描述阶段之间流动什么，不描述怎么取、怎么执行
- **适配层不含工作流策略** —— Wind 适配器只负责取数，不判断"接下来该干什么"
- **编排层独占状态迁移** —— 其他任何模块都不能直接改会话状态
- **接口层只做校验与分发** —— API 处理器不写业务逻辑

### 3.3 四条信任边界

| 边界 | 内侧 | 外侧 | 隔离手段 |
|---|---|---|---|
| **B1 用户输入** | 后端逻辑 | 研究想法、研报 PDF | 契约校验；文件类型/大小/页数限制；研报内容永不作为指令 |
| **B2 模型输出** | 执行计划 | 模型返回的 JSON | 强制结构验证；只接受登记算子；证据 ID 必须真实存在；字段必须经验证与确认 |
| **B3 执行面** | 密钥、数据库、网络 | 计算过程 | 独立进程、无网络、无密钥、资源限额、manifest 签名校验 |
| **B4 数据出境** | 内部数据 | 外部模型服务 | 默认不发送原始数据；只发送最小必要上下文；支持全本地模式；审计不留正文 |

**B4 是本版新增的边界**。前三条防的是"外面的东西进来搞破坏"，B4 防的是"里面的东西出去"—— 详见 §13.4。

### 3.4 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI + Pydantic | 与量化生态一致；契约即校验 |
| 元数据 | SQLite + 迁移工具 | 单机原型，零运维；数据量小 |
| 计算与工件 | pandas / numpy / Parquet | 列式存储，带 schema，适合工件链哈希 |
| Wind 接入 | MySQL 只读账号 | 已有副本；只读账号限制破坏面 |
| 字段检索 | 本地元数据目录 + BM25 + 中文分词 | 离线、确定性、可解释 |
| 研报 | PDF 文本提取 + OCR | 文本型优先，扫描件降级处理 |
| 前端 | React + TypeScript + Vite + 组件库 | 类型由后端契约生成，契约变更即编译错误 |
| 部署 | 单机容器编排 | 一个文件描述全部拓扑，Worker 断网可验证 |

**为什么是模块化单体而不是微服务**：单人一个月，微服务的隔离收益不足以抵消运维和联调成本。唯一拆出去的进程是 Worker —— 它是**安全边界**而不是扩展性边界。

## 4. 主流程与状态管理

### 4.1 主工作流

```text
 1. 接收研究请求（信封 + 想法）或研报
 2. 模型产出结构化因子草案（只含语义字段）
 3. 后端渲染 canonical_formula，程序规则独立审计歧义
 4. 用户确认公式、变量、方向、窗口、预处理顺序、时间口径
 5. 把变量拆解为数据需求
 6. 分层检索 Wind 字段，附带业务解释与样本证据
 7. 用户确认字段与口径
 8. 确定性规划器生成取数计划
 9. 后端取数 → 中间工件 → 构建并签名 manifest
10. Worker 隔离执行 → 三层校验 → 保存结果与复现记录
```

### 4.2 状态机设计

因子开发是**长时、多轮、可中断、必须可追溯**的流程。用"当前状态字段 + 就地更新"会丢失中间过程，也难以保证并发安全。因此采用事件溯源：**事件日志不可变，当前状态永远是事件流的归约结果。**

主干状态：

```text
创建 → 解析中 → 需要澄清 → 等待公式确认 → 字段检索中 → 等待字段确认
     → 规划中 → 待执行 → 执行中 → 校验中 → 完成 / 失败
```

设计规则：

- **合法迁移穷举，其余一律拒绝** —— 用一张显式的转移表定义每个 `(状态, 事件)` 的结果，缺席即非法。这样"从失败状态直接跳到完成"这类错误在类型层就不可能发生。
- **确认必须携带版本号** —— 过期的确认被拒绝而不是静默覆盖。
- **阻塞性歧义未解决不能进入字段检索。**
- **失败保留现场** —— 原阶段、输入工件、错误证据都保留，修订后生成新版本。
- **下游模块只消费已完成工件** —— 因子检验、因子库、指数不侵入主状态机。

### 4.3 修改、回退与级联失效

真实用户不会一路向前走完。他们会确认公式后改公式、确认字段后发现口径错、改股票池、改日期、复制一个因子做新版本、取消正在跑的任务。

因此除了向前推进的事件，还需要一组**修订事件**：公式修订、字段修订、请求修订、预处理修订、时间口径修订、股票池修订、日期区间修订、执行取消、会话克隆、重新运行。

**关键设计：上游修订必须使下游产物失效。**

| 修订内容 | 失效范围 |
|---|---|
| 公式 | 字段选择 → 执行计划 → manifest → 输入工件 → 执行结果 → 校验结果 |
| 字段 | 执行计划 → manifest → 输入工件 → 执行结果 → 校验结果 |
| 日期区间 | 执行计划 → 输入工件 → 执行结果 → 校验结果 |
| 股票池 | 字段样本验证 → 执行计划 → 输入工件 → 执行结果 |
| 预处理 | manifest → 执行结果 → 校验结果 |
| 时间口径 | 执行计划 → 前向收益定义 → 执行结果 → 因子检验结果 |

**归约器必须带业务语义。** 简单的"最后一个非空值获胜"会留下陈旧产物 —— 新公式已确认，快照里却还挂着旧字段和旧执行计划。归约器要显式定义：哪些事件写入新值、哪些事件使旧值失效、哪些事件清空下游、哪些旧工件转为历史版本。

历史版本不可覆盖，支持查看版本差异和回退；回退后重新生成下游工件，不复用已失效的旧结果。

### 4.4 版本与并发

每次状态变更携带 `expected_version`。追加事件时在**同一个事务内**完成三件事：归约出当前状态、比对版本、校验迁移合法性。任何一项不通过都不留下记录。

检查顺序刻意设计为先版本后迁移 —— 这样过期的浏览器标签页拿到的是"版本过期，请刷新"，而不是含糊的"非法迁移"。

## 5. 因子语义层

### 5.1 从想法到因子定义

模型看到的是一个**删减过的结构**：只有语义字段（因子名、假设、方向、调仓频率、公式 AST、变量清单及其数据语义），**没有**资产类型、股票池、日期区间、频率这些来自用户表单的可信信封。

这样模型不可能把股票池从沪深 300 悄悄改成全市场 —— 它根本没有那个字段。信封由程序合并进最终定义。

提示词明确要求：**不确定的字段留空，不要编造**。

### 5.2 公式表示：AST 唯一，canonical 渲染

这是本版的重点修订。

```text
模型只产出 formula_ast
  → 后端校验 AST
  → 后端从 AST 确定性渲染 canonical_formula
  → 用户确认 canonical_formula
  → 执行同一份 AST
```

三个产物的地位截然不同：

| 产物 | 来源 | 地位 |
|---|---|---|
| `formula_ast` | 模型产出 + 后端校验 | **唯一可执行内容** |
| `canonical_formula` | 后端从 AST 确定性渲染 | **用户确认的正式公式** |
| `formula_explanation` | 模型产出 | 自然语言解释，仅展示，不参与确认与执行 |

用户在界面上看到并签字的那行公式，是**由实际要执行的 AST 直接渲染出来的**。渲染是确定性的：同一棵 AST 永远渲染成同一个字符串。这样"确认的"和"执行的"在结构上不可能分叉。

### 5.3 公式合法性三重校验

AST 通过结构约束（每个节点只能是变量引用、数值常量、算子调用三者之一，且不允许多余字段）保证良构，但良构不等于合理。还要三重校验：

**变量绑定校验**
- AST 引用的变量必须全部在变量清单中定义；引用未定义变量直接阻塞
- 变量逻辑名不得重复，须符合统一命名规范
- 定义了但未被 AST 使用的变量给出警告
- 变量到字段的映射必须在生成执行计划前完成确认

**结构复杂度校验**
- 节点总数、递归深度、单算子参数数量均设上限
- 滚动窗口大小设上限，拒绝异常大的时间窗口
- 拒绝空参数、非法参数类型、未登记算子

**数值合法性校验**
- 权重与字面量必须是有限数，拒绝 `NaN` / `inf` / `-inf`
- 除零、对数非正输入必须有确定的处理策略（统一转缺失值或阻塞）
- 公式的实际方向与声明的 `direction` 做一致性检查

### 5.4 预处理流水线：与公式分离，顺序显式

**问题**：原设计里"去极值 / 标准化 / 行业中性化"同时存在于两处 —— 既是 AST 算子，又是预处理开关。这造成执行歧义（AST 已经 zscore 了一次，全局规则又要求标准化，到底做几次？），而且布尔开关**无法表达顺序** —— 先中性化再标准化和先标准化再中性化，结果不同。

**方案**：从契约层消除双重表达。

- **AST 只负责因子的数学表达**，移除 `winsorize` / `zscore` / `industry_neutralize` 三个算子
- **预处理统一放进有序流水线**，每步显式声明操作、作用对象、方法、顺序和参数

```yaml
preprocessing_pipeline:
  - order: 1
    operation: winsorize
    target: variables        # 对原始变量分别处理
    method: mad
    parameters: { n_sigma: 3 }

  - order: 2
    operation: industry_neutralize
    target: factor           # 对公式算出的最终因子处理

  - order: 3
    operation: zscore
    target: factor
```

`target` 区分**变量级处理**和**因子级处理**，这是布尔开关表达不了的关键语义。

配套规则：每个操作必须有明确顺序；同一目标不允许重复执行相同操作（除非用户显式要求）；系统检测重复标准化、重复去极值、重复中性化；流水线本身版本化并可追溯；用户确认时展示完整顺序。

保留在 AST 中的算子（11 个）：算术五则、对数、截面排名、滚动收益、滚动波动、滚动均值、缺失值填充。

### 5.5 时间口径

即使一个字段都没读错，仍然可能通过错误的信号时点和交易时点形成**隐性未来函数**。典型问题：T 日收盘价算出的因子，能不能用于 T 日收益？盘后发布的财务公告，能不能在公告日当天使用？

原设计处理了报告期、公告日、历史成分、预热窗口，但没有完整定义信号与交易的时间关系。本版补上：

| 概念 | 含义 |
|---|---|
| 观测时点 | 原始数据的时点（T 日收盘价、某报告期数据） |
| 信息可得时点 | 该信息在真实市场中可被研究者获得的时点（T 日收盘后、公告日盘前/盘后） |
| 信号日 | 系统正式形成因子信号的日期 |
| 交易日 | 信号允许用于交易或收益观察的最早日期 |
| 执行价格 | 默认成交价口径（次日开盘、次日收盘、VWAP，或仅用于收益计算） |
| 前向收益起止 | 未来收益的观察区间 |

**首期默认口径**：日频行情因子在 T 日收盘后计算，信号日为 T，最早交易日为 T+1，执行价格取次日开盘价，前向收益从 T+1 开盘算起；财务数据按实际公告可得日生效。

附加规则：
- 财务公告区分盘前 / 盘中 / 盘后；**无法获取具体发布时间时采用保守规则**，默认不在公告日当日使用盘后公告
- 同一实验中所有因子必须使用一致的时间口径
- 时间口径写入执行计划与结果工件，因子检验页面必须展示收益起止口径
- 时间口径变化导致执行计划与结果失效，需重新运行

### 5.6 歧义澄清

模型提出因子定义，澄清引擎**独立审计**它有没有阻塞性歧义。规则是纯程序逻辑，因此阻塞行为稳定、可测、不依赖模型。

判据采用"**模糊词命中 + 具体词未命中**"双条件：用户说"盈利质量因子"要追问；用户说"盈利质量（用 ROE_TTM）"口径已明确，再追问就是噪音。单条件规则会在后一种情况下误报，这类误报最伤体验。

| 类型 | 是否阻塞 | 判据 |
|---|---|---|
| 口径歧义（盈利 / 估值 / 增长等） | 阻塞 | 猜错会让因子在语义上变成另一个因子 |
| 因子方向未声明 | 阻塞 | 方向反了，结论就反了 |
| 时间窗口、权重、报告期、股票池歧义 | 阻塞 | 影响可比性和正确性 |
| 调仓频率未声明 | 非阻塞 | 有合理默认值，显式展示留痕即可 |

**候选项来自口径登记表**（§14.2），不硬编码在代码里 —— 这样口径可以被单独复核和版本化。

## 6. 数据发现层

### 6.1 数据源分工

Wind 提供两类资源，职责必须分开：

```text
WDS（数据字典服务）    → 回答"应该查什么"：字段元数据与业务口径
Wind MySQL 副本        → 回答"如何取出真实数据"：实际取数
```

原设计只用了导出的字段索引（表名 + 字段名），缺少资产类型、频率、业务解释、单位、时间口径，导致检索的过滤能力不足。本版把 WDS 正式纳入架构。

### 6.2 元数据目录

新增元数据同步与目录模块，职责是：从 WDS 整理导出字段元数据 → 本地结构化保存 → 与现有字段索引合并 → 为检索提供完整业务信息 → 版本化管理。

**运行时不实时访问 WDS**：

```text
开发阶段访问 WDS → 整理导出 → 保存到本地目录 → 运行时查本地 → 未覆盖字段人工补充
```

每条元数据记录的内容包括：表中英文名、字段中英文解释、单位、频率、资产类型、主键与关联键、证券代码字段、交易日字段、公告日字段、报告期字段、是否衍生字段、数据更新方式、可得性说明、适用范围、是否存在修订版本、元数据来源与版本。

这些信息直接决定了后面几件事能不能做对：过滤能不能生效、时间角色能不能自动推断、单位换算对不对、点时字段找不找得到。

### 6.3 字段发现漏斗

字段发现按置信度从高到低分层，**逐层收敛**：

```text
① 已注册专用函数的精确语义匹配
      ↓ 未命中
② 人工维护的业务词别名
      ↓ 未命中
③ WDS 本地元数据目录（业务解释、单位、频率、资产类型）
      ↓ 未命中
④ BM25 词法检索（中文分词 + 英文驼峰/下划线切分）
      ↓ 候选集
⑤ information_schema 校验（表、列、类型真实存在）
      ↓ 通过
⑥ 数据样本验证（按数据形态采样）
      ↓ 附证据
⑦ 用户确认
```

前四层负责**召回**，后三层负责**证伪**。任何字段进入执行计划前必须走完全程。

### 6.4 Schema 验证与数据存在性验证分离

这是本版的另一处重要修订。

**原问题**：统一用"3 只证券 × 5 个交易日"采样，只适合日频行情。财务字段在 5 个交易日内可能没有任何记录，公告事件在短区间内可能为空，指数成分变化需要覆盖调仓日。系统会把"样本区间恰好没数据"误判成"字段无效"。

**修正一：两类验证分开**

| 验证 | 检查内容 |
|---|---|
| Schema 验证 | 表存在、字段存在、字段类型、时间字段、代码字段、主键或业务键、字段是否适用于当前查询形状 |
| 数据存在性验证 | 样本区间有无数据、非空率、重复键、数值范围、单位、时间覆盖、返回行数、样例值 |

**修正二：采样策略按数据形态制定**

| 数据类型 | 采样策略 |
|---|---|
| 日频行情 | 3 只证券 × 5–20 个交易日 |
| 季度财务 | 3 只证券 × 8 个报告期 |
| 年度数据 | 3 只证券 × 5 个年度报告期 |
| 公告事件 | 3 只证券 × 2–3 年 |
| 静态信息 | 10 只不同板块证券的截面 |
| 区间数据 | 至少覆盖一次进入和退出事件 |
| 指数成分 | 至少两个历史调仓日 |
| 行业归属 | 至少一次行业变更或多个历史截面 |
| 基金数据 | 至少一个完整披露周期 |

**修正三：返回状态细化**，不再是通过/失败二值：

```text
SCHEMA_VALID_DATA_PRESENT        字段有效且样本有数据
SCHEMA_VALID_NO_DATA_IN_SAMPLE   字段有效，但当前样本区间无数据
SCHEMA_VALID_DATA_SPARSE         字段有效，数据稀疏
SCHEMA_INVALID                   表或结构不符
FIELD_INVALID                    字段不存在
TIME_ROLE_INVALID                时间角色不适用
```

"字段存在但样本为空"要如实呈现给用户，而不是判定为错误。

### 6.5 受控查询：六种形状

**系统不存在任意 SQL 入口。** 专用函数未覆盖的字段，只能通过六种预定义查询形状访问：

| 形状 | 用途 | 必需时间角色 |
|---|---|---|
| 点区间 | 日频行情、日频衍生指标 | 观测日 |
| 报告期 | 财务数据（点时） | 报告期（可选公告日） |
| 公告区间 | 按公告日取数 | 公告日 |
| 区间重叠 | 历史指数成分、行业归属 | 区间起、区间止 |
| 静态查找 | 证券静态信息 | 无 |
| 截面基准 | 截面基准日取最新值 | 观测日 |

**四道防线**：

1. **标识符白名单** —— 表名、字段名、角色字段必须匹配严格的小写标识符正则；引号、分号、空格、`UNION` 全部无法通过
2. **存在性校验** —— 标识符合法不等于真实存在，还要查 `information_schema` 确认
3. **形状角色完备性** —— 每种形状必需的时间角色缺一不可
4. **值全部参数化** —— 证券代码、日期全部作为参数传入，**没有任何用户值被拼进 SQL 字符串**

**点时正确性内建在报告期形状里**：给定基准日时自动追加"公告日 ≤ 基准日"条件；同一报告期多次公告（财报修正）时按公告日去重取最新版本。

### 6.6 函数规划

规划器把"确认后的因子定义 + 确认后的字段"编译成确定性取数计划。

**优先级固定**：已注册专用函数 → 已确认字段的受控通用查询 → 拒绝。字段未经确认直接失败，不做任何猜测。专用函数优先是因为它们经过验证、有缓存、有明确的返回结构。

**规划器要主动补齐用户不会说但必须做的事**：

| 补齐项 | 原因 |
|---|---|
| 数据调用前先取**历史**指数成分 | 用今天的沪深 300 成分回测三年前 = 幸存者偏差 |
| 从最大滚动窗口反推预热起始日 | 20 日动量在区间首日就要有值，需要多取前 20 个交易日 |
| ST / 停牌过滤 | 来自预处理流水线的股票池规则 |
| 保留报告期与公告日字段 | 点时可得性的证据 |
| 写入时间口径 | 信号日与交易日的关系必须固化进计划 |

**硬红线**：无法证明点时可得的财务数据不能进入计划 —— 这是规划期直接失败，不是警告。

## 7. 执行层

### 7.1 唯一执行载体：manifest

这是本版最大的架构简化。

**原设计**：后端生成一份 Python 源码 → Worker 用子进程执行它 → 为此需要源码 AST 白名单、动态 import 检查、源码参数解析、以及"界面展示的代码和实际执行的代码逐字节一致"的证明。

**问题**：生成的 Python 实际上只是一层固定包装 —— 嵌入因子定义和执行计划，然后调用平台内部的运行时。真正的计算逻辑在平台自己的代码里，生成的源码不承担任何业务逻辑。用户也不能修改它再执行（界面只读）。

也就是说：**为了证明安全，先制造了一个需要额外安全处理的对象。**

**修正后**：

```text
后端构建 manifest → 校验结构与版本 → 签名 → 入队
Worker 读取 manifest → 验签 + 校验 schema/版本/哈希 → 直接调用运行时 → 输出结果
```

manifest 包含：因子定义、执行计划、预处理流水线、时间口径、字段选择、输入工件哈希、各项版本号、签名、执行参数。**它是平台唯一实际执行的对象。**

**安全收益**：可以删除子进程动态执行、源码 AST 白名单、动态 import 检查、源码参数解析，以及相当一部分沙箱攻击面。

**仍然保留**：公式 AST 校验、manifest 结构校验、工具白名单、查询范围限制、无密钥 Worker、无网络 Worker、资源限制、输入输出哈希校验。

### 7.2 用户导出产物

代码可读性的需求依然存在（用户要审查、复现、答辩展示）。因此把它降级为**导出产物**：

```text
manifest.json   → 平台内部执行载体
factor.py       → 由同一份 manifest 确定性生成，供用户审查/复制/下载/在批准环境中复现
```

两者同源，但 `factor.py` 不进入内部执行路径。界面上展示的仍然是完整可读的程序，用户拿到的是能在自己环境跑的东西 —— 需求满足了，攻击面没有了。

### 7.3 取数与计算的职责切分

| 阶段 | 执行者 | 持有 | 输入 | 输出 |
|---|---|---|---|---|
| 取数 | 受信任后端 | Wind 凭据 | 已校验的执行计划 | 中间 Parquet |
| 计算 | Worker | 无密钥、无网络 | 中间 Parquet + manifest | 结果 Parquet + 结果 JSON |

这条切分是安全模型的核心：**Worker 永远不需要碰数据库**。所有数据在入队前已由后端取好写成 Parquet，Worker 只做纯计算，因此可以合法地被剥夺一切外部访问能力。

### 7.4 任务队列：租约、幂等、取消、超时

队列用文件系统实现（`pending` / `running` / `completed` / `failed` 四个目录 + 原子重命名抢占），零依赖、零凭据、零网络 —— 恰好符合 Worker 的隔离要求。

原子重命名解决了"两个 Worker 抢同一个任务"，但解决不了**崩溃**：Worker 把任务移进 `running` 后进程挂掉，任务会永久滞留。因此补上四项机制：

**任务租约**
任务描述中记录领取者、领取时间、租约到期时间、尝试次数、输入哈希、幂等键、超时上限、最大重试次数、工件保留期限等。

恢复流程：扫描 `running` → 判断租约是否过期 → 检查是否已有完整结果 → 有则转 `completed` → 无结果且未达最大重试则放回 `pending` → 达到上限则标记 `failed` → 记录恢复事件与原因。

**幂等键**
由会话 ID、会话版本、manifest 哈希、输入哈希共同生成。重复请求不产生多个等价任务。

**取消**
用户可请求取消；`pending` 任务直接标记取消；`running` 任务写入取消标记，Worker 在安全检查点读取；取消后不得写入正式结果。

**超时与清理**
每个任务设运行上限，超时终止并返回结构化错误，是否可重试由错误分类决定。工件按类型设定保留期限（上传 PDF、中间文本、输入输出 Parquet、日志、错误工件、临时文件、导出代码）。定期检查磁盘可用空间，达阈值时停止接收新任务、优先清理过期临时工件、保留不可变正式工件并记录清理日志。

### 7.5 Worker 隔离

- 环境变量采用**白名单构造**（只有运行必需的两三个无害变量），而不是"复制现有环境再删掉密钥"—— 后者一旦漏删就泄密
- 施加 CPU 时间、内存、文件大小限制
- 独立校验 manifest 签名与结构，不信任上游已经验过
- 生产部署中容器网络模式为 `none`，即使代码里有网络调用也没有可用网络栈

## 8. 校验层

三层校验都产出结构化发现，每条带级别、错误码、说明和证据。**级别语义**：错误阻塞流程；警告不阻塞但必须在界面显示、用户可显式接受；提示仅供参考。

### 8.1 数据层：取数对不对

区间覆盖、证券数量、重复键、缺失率、单位、数量级、全零或常数、极值、历史成分正确性、公告日存在性、未来数据、复权口径、字段口径。

其中**重复键必须阻塞** —— `(日期, 代码)` 重复通常意味着关联出错或财报多版本未去重，这类错误会静默污染整个因子。

### 8.2 公式层：算法对不对

截面/时序轴语义、窗口合法性、方向一致性、权重、除零、缺失值、中性化、重复标准化、未来价格、财务数据可得性。

两个重点：

- **点时泄漏必须阻塞** —— 在公告日之前使用了财务数值，直接失败
- **重复标准化检测** —— 先 zscore 再 rank 再 zscore 会把信号压平，是常见但不易发现的建模错误。本版把预处理改成有序流水线后，这类问题在契约层就大幅减少了

### 8.3 结果层：结果可信不可信

覆盖率、分布、Top/Bottom 样本、原始变量对照、因子时间变化、耗时、查询行数、警告。

本版新增三条与口径治理配套的规则：

| 规则 | 级别 | 触发条件 |
|---|---|---|
| 量级不合理 | 错误 | 结果超出口径登记表声明的合理区间（如 ROE 算出 3000%） |
| 参照对拍不一致 | 警告 | 与独立算路的结果差异超阈值（如自算 PE 与 Wind 自带 PE 对不上） |
| 依赖未复核口径 | 警告 | 因子引用了尚未复核的口径定义 |

**参照对拍是无人全程复核条件下最有价值的机器化替代**：它不需要领域专家在场，却能抓住相当一部分口径错误。

## 9. 可追溯与可复现

### 9.1 为什么程序哈希和结果哈希不够

只记录"哪段程序"和"什么结果"，无法回答：用的是哪一版输入数据？查询发生在什么时候？数据库后来是否修订过？字段元数据和口径定义是哪个版本？

Wind 财务数据会被修订，同一份程序在不同时间跑出的结果可能不同。因此复现记录必须覆盖**输入侧**。

### 9.2 工件链

每次执行产出一条不可变的工件链：

```text
query_manifest.json  →  raw_input.parquet  →  aligned_input.parquet
                     →  factor_output.parquet  →  validation_report.json
```

每个工件记录：文件哈希、大小、行数、列数、结构、生成时间、来源、**上游工件哈希**。上游哈希把整条链锁在一起，任何一环被替换都能被发现。

### 9.3 复现记录

因子工件除了程序哈希和结果哈希，还要保存：输入工件哈希、查询时点、来源库与表、来源字段、查询参数、数据区间、行数、输入结构与非空率、查询计划哈希，以及各项版本号 —— 因子定义版本、执行计划版本、预处理版本、时间口径版本、字段元数据版本、口径定义版本、适配器版本、代码提交号、运行时版本。

这样才能真正证明：**这份结果由这份程序，基于这一版输入数据和这一版字段口径生成。**

## 10. 研报入口

### 10.1 能力边界

卖方研报里的公式可能出现在图片、多栏排版、表格、上下标、希腊字母、公式截图、页眉页脚、脚注、跨页位置、扫描页。**通用 OCR 对数学公式的识别并不稳定。** 如果笼统承诺"根据研报识别因子公式"，验收时遇到公式全是图片的研报就会预期落空。

因此首期边界写清楚：

> **首期支持正文中可复制、变量定义明确的中英文文本型研报；图片公式、复杂数学排版和扫描版研报仅识别正文提示，并要求人工确认公式。**

| 首期支持 | 首期不承诺自动准确识别 |
|---|---|
| 可复制正文文本 | 纯图片公式 |
| 公式以普通文本或可解析字符存在 | 复杂 LaTeX 排版 |
| 变量定义明确 | 多层上下标、大量希腊字母 |
| 因子口径在正文有说明 | 扫描版 PDF |
| 可定位页码 | 跨页公式 |
| 中英文文本 | 复杂多栏错序、公式截图 |
| 简单表格旁的变量说明 | 表格中高度压缩的公式 |

### 10.2 处理流程

1. 校验文件签名、类型、大小、页数；加密文件无密码直接拒绝；**绝不执行嵌入内容**
2. 文本型直接提取块级文本，保留页码与位置证据
3. 文本密度低于阈值的页才走 OCR（限定渲染精度、每份文件 OCR 页数上限、保留置信度）
4. 按公式/变量/样本/预处理相关词给文本块打分排序
5. 只把**有界的**高分片段（带页码 ID）送模型
6. 每个抽取出的变量必须携带证据 ID；**输入中不存在的证据 ID 一律判非法** —— 这是防幻觉的硬检查
7. 研报没写的内容（如调仓频率）标为歧义交用户确认，绝不填一个看起来合理的值

### 10.3 低置信度的处理

无法可靠识别公式时：

```text
识别到可能存在因子公式 → 提取附近正文与页码 → 标记"需人工确认"
→ 允许用户手动输入或修改公式 → 转换为 AST
```

抽取结果记录状态、置信度、来源页码、原文片段和风险提示（如"公式包含图片和上下标，自动识别可能不准确"）。

**系统不得在公式识别置信度不足时直接进入执行。**

**安全立场**：研报内容始终是不可信数据，不能改变系统指令、触发工具调用或绕过确认。

## 11. 交互设计

### 11.1 核心原则

前端**只渲染后端状态**，不自行判断业务迁移。所有"下一步该做什么"的判断都在后端状态机里。前端做的是把会话状态映射成界面上第几步高亮 —— 这个映射是纯函数，可以脱离界面单独测试。

前端类型由后端契约生成。契约改了而前端没跟上，是编译错误而不是运行时崩溃。

### 11.2 页面

| 页面 | 内容 |
|---|---|
| 因子工作台 | 顶部参数区；左栏公式/代码/结果；右栏对话/步骤/确认卡 |
| 研报提取 | 上传、页码证据、抽取结果、进入统一工作流 |
| 因子库 | 版本化因子、字段、公式、代码、工件、运行记录 |
| 因子检验 | IC、Rank IC、分组收益、换手率、覆盖率 |
| 指数 | 组合规则、调仓日、成分、权重导出 |
| 管理 | 用户、角色、模型服务状态、系统健康度 |

### 11.3 确认卡

- **澄清卡** —— 阻塞问题分组呈现，未回答不能继续
- **公式确认卡** —— 展示 canonical_formula、变量、方向、窗口、**完整预处理顺序**、时间口径
- **字段候选表** —— 来源层级、表、字段、中文业务解释、时间角色、单位、Schema 状态、样本统计与状态（含"字段有效但样本区间无数据"）
- **代码面板** —— 只读展示导出产物，支持复制与下载
- **结果面板** —— 分布、覆盖率、Top/Bottom、样例行、耗时、校验发现、工件下载

**所有确认动作携带当前可见版本号**：界面上是版本 8 就提交版本 8；后端已到 9 则返回冲突并提示刷新。用户永远不会在过期视图上做出被静默接受的确认。

### 11.4 进度与恢复

会话事件全部持久化，因此进度推送做成**可恢复**的：推送事件带序号，断线重连时先补发历史事件再继续。

推送只是加速器不是必需品 —— 所有关键状态都能通过普通查询拿到，推送中断最多是进度更新变慢，不会丢状态。

## 12. 研究扩展功能

### 12.1 错误分类与两轮修复

错误分七类：输入、字段、空数据、时间口径、公式、资源、基础设施。

**只有参数与公式类错误可由模型提出修订**：无效参数、公式类型错误、除零策略、对齐错误。字段不存在、空数据、基础设施故障不可自动修复 —— 那些需要人来决定。

**最多两轮，硬上限**。每轮产生新版本且必须重新确认后才能执行。上限的理由：修复循环最容易失控，两轮修不好说明问题不在参数层面。

### 12.2 因子检验

指标：Pearson IC、Spearman Rank IC、分组等权收益、多空价差、覆盖率、单边换手率。

**无前视是第一约束**：前向收益按 §5.5 的时间口径 shift，按日期和代码对齐；截面观测数不足的日期直接拒绝。检验页面必须展示收益起止口径。

边界：日频 A 股、中小规模区间、固定分组。

### 12.3 因子库

已发布版本不可覆盖；修改后的完成会话发布为新版本；工件复制进版本化的不可变目录。

存储分工：元数据库存标识、版本、来源会话、定义、字段映射、计划、各项哈希与版本号、创建者、时间戳；Parquet 存工件。

### 12.4 多因子与指数

输入必须是已完成**且已复核**的因子库版本。流程：对齐日期与股票池 → 统一方向 → 逐个标准化 → 拒绝非有限权重 → 权重归一化。

指数规则支持 Top N、等权或因子得分加权、月度/周度调仓、CSV 导出。**不含实盘下单。**

只支持线性加权，不支持任意图计算。

### 12.5 权限

两角色：管理员（管理用户与模型服务，查看服务健康度、调用次数、成本、失败率）、研究员（管理自己的会话、研报、因子、分析、指数）。

密码用强哈希算法；会话 ID 签名后存 HttpOnly + SameSite Cookie，只存哈希与过期时间，登录时轮换；Cookie 认证的变更请求需 CSRF 令牌。不提供企业 SSO。

## 13. 安全与合规

### 13.1 凭据

真实密钥只进本地环境文件，仓库只提交空值模板。所有密钥字段用保密类型包装，日志与异常不泄露。**解密操作在代码库中只出现一处** —— 想知道明文可能出现在哪里，只需要看那一行。

历史遗留的明文凭据采用**值盲脱敏**：按键名和连接串形态匹配替换，从不按字面值匹配，因此明文从未进入过对话记录、工具参数或提交历史。脱敏后用密钥扫描工具与结构化检索双重验证。

### 13.2 SQL

见 §6.5 的四道防线。**无条件禁止任意 SQL。**

### 13.3 执行隔离

见 §7。manifest 直接执行取代生成代码执行后，攻击面显著收窄；保留的防线是 manifest 验签与结构校验、工具白名单、查询范围限制、无密钥无网络 Worker、资源限制、输入输出哈希校验。

### 13.4 外部模型的数据边界（B4）

原设计防住了"外面进来"，但没定义"里面出去"。系统会处理卖方研报、Wind 字段元数据、Wind 原始字段值、内部研究想法、用户上传文件、运行错误与日志 —— **哪些内容可以发送给外部模型服务，必须明确。**

**默认禁止发送**：Wind 原始数据、数据库连接信息、密钥、内部代码、未经授权的内部文档、完整结果数据。

**允许发送的最小内容**：字段元数据、公式结构、用户明确输入的研究想法、必要的字段说明、经裁剪和脱敏的研报片段、必要的错误摘要、不含敏感值的结构化上下文。

**研报处理规则**：上传前确认授权范围；受版权限制的文档不使用个人账户；只发送与因子相关的高分片段，不默认发送完整 PDF；原文进入模型前做敏感信息扫描；调用日志不保存完整正文。

**本地模式**：系统必须支持"本地解析，不调用外部模型" —— 该模式下 PDF 只做本地文本提取，字段检索只用本地目录，用户手动确认公式，不向外部发送任何正文。

**审计**：记录调用时间、服务商、模型、输入类型、是否脱敏、文本长度、Token 数、成本、结果、失败原因；**不默认保存完整敏感正文**。

以下问题需要在正式接入外部模型前确认：是否允许发送完整研报、是否允许发送 Wind 原始字段值、是否需要脱敏、服务商是否保留输入、是否必须使用公司批准的账户、是否允许个人账户、哪些内容只能本地处理。

### 13.5 禁止清单（无条件）

任意 SQL、动态求值与执行、系统命令、任意网络访问、任意文件访问、未登记的函数或算子。**不接受"为了赶进度"作为放开理由。**

## 14. 口径治理与验收

### 14.1 角色安排

准确表述是：

> **暂无专职研究人员全程参与；由开发者完成口径整理、证据生成和初步核验，关键指标及最终验收由带教老师进行抽样确认。**

开发者本身承担量化研究工作，带教老师在关键节点做最终抽样确认。这不等于没有领域复核，但也意味着**不能假设每一条口径都会被逐条审查** —— 因此需要把口径显式化，让抽样确认能高效进行。

### 14.2 口径登记表

问题在于口径判断原本散落在三处：澄清规则的代码常量、字段别名映射、标准案例夹具。三处各自演化，**没有一处是能被非程序员读懂并签字的形态**。

解法是抽出单一的、机器可读的口径登记表：

```yaml
ROE_TTM:
  display_zh: 净资产收益率（TTM）
  definition: 归母净利润(TTM) / 期末归母股东权益
  wind_table: asharefinancialindicator
  wind_field: s_fa_roe
  time_role: report_period
  announcement_field: ann_dt
  unit: percent
  plausible_range: [-100.0, 100.0]   # 供结果层量级校验
  reference_check: null              # 可选：独立算路，用于对拍
  review_status: unreviewed
```

它同时承担四个作用：**澄清卡的候选项来源**、**字段映射的权威定义**、**结果层量级校验的阈值来源**、**对拍参照的配置**。改一处口径，全链路一致。

### 14.3 三值状态与闸门

| 状态 | 含义与权限 |
|---|---|
| `unreviewed` | 尚未复核。**可用于原型测试和内部试算**；不能作为正式发布结果；界面必须明确标记"未复核" |
| `reviewed` | 已由带教老师或指定复核人确认。可用于正式演示、因子库和后续发布。须保存复核人、复核时间、复核意见 |
| `disputed` | 已知字段、公式或业务口径存在问题。**禁止执行、禁止发布、禁止进入因子库、禁止进入多因子与指数**，不允许通过普通操作绕过 |

**已知的错误映射直接标 `disputed` 并阻塞，而不是仅发警告** —— 例如把"流通市值"映射到流通股本字段、把"经营活动现金流"映射到间接法起点净利润。业务含义与字段含义明显不一致的映射不应该被允许执行。

复核信息随因子工件保存：复核状态、复核人、复核时间、复核意见、证据版本。

### 14.4 验收证据包

抽样确认要高效，就必须让复核人拿到**自足的材料**。每个验收案例产出一个证据包：原始请求、确认后的因子定义、canonical 公式、本案例引用的口径条目快照、字段血缘（变量 → 表.字段 → 时间角色 → 公告日字段）、导出程序及哈希、三层校验完整报告、结果 Top/Bottom 样例与覆盖率分布、对拍差异。

**交付边界必须写清楚**：平台交付的是"机器可验证的正确性"（公式语义、点时可得性、字段真实性、执行隔离、结果量级、可复现性），**不是"因子的业务有效性"** —— 后者需要领域签字。避免把"跑通了"误读成"口径对了"。

## 15. 质量保障

### 15.1 案例集

10 个案例够做单元测试和基础流程验收，但**不足以证明一般化能力** —— 尤其澄清规则含硬编码成分时，容易出现"只对现有案例定向通过，面对新表达就不稳定"。

目标案例集：

| 类别 | 数量 | 覆盖 |
|---|---|---|
| 自然语言因子 | 20–30 | 价量、估值、盈利、增长、质量、复合因子、历史成分、点时财务；不同中文表达；少量英文 |
| 歧义案例 | 5–10 | 盈利质量、估值、增长口径、时间窗口、因子方向、权重、调仓频率、报告期、股票池 |
| 中文研报 | 3–5 | 文本型公式、公式缺失、变量定义明确、变量定义分散、复杂排版需人工确认 |
| 英文研报 | 3–5 | 同上 |

**隐藏验收集**：另建一组开发期间不可查看标准答案的案例，最终统一运行。目的是防止对测试集定向调参，评估真实的一般化能力。

### 15.2 量化指标

不只报告"能否运行"，还要报告语义和点时正确性：

| 维度 | 指标 |
|---|---|
| 结构化解析 | 因子定义结构正确率、AST 变量绑定正确率、AST 合法率、canonical 公式一致率、方向识别准确率 |
| 澄清能力 | 阻塞性歧义召回率与准确率、不必要追问率、默认值使用正确率、确认后修订成功率 |
| 字段与函数 | 字段 Top-1 / Top-3 准确率、Schema 验证通过率、函数规划准确率、专用函数优先匹配率、通用查询计划正确率 |
| 执行与安全 | 执行成功率、点时泄漏拦截率、未来函数拦截率、错误分类准确率、任务恢复成功率、幂等执行正确率 |
| 研报解析 | 公式提取准确率、变量提取准确率、证据页码准确率、中英文处理成功率、"需人工确认"识别准确率 |
| 效率与成本 | 平均响应时间、平均调用次数、平均 Token 消耗、平均成本、字段检索耗时、执行耗时、与人工开发耗时对比 |

**评价方式**：开发集、验证集、隐藏测试集分开；报告总体指标的同时报告失败案例；区分模型错误、字段错误、数据错误和执行错误。

### 15.3 测试分层

| 层 | 覆盖 | 需真实凭据 |
|---|---|---|
| 契约测试 | 数据结构约束、AST 形状互斥 | 否 |
| 纯逻辑测试 | 状态迁移、级联失效、澄清规则、公式算子、预处理顺序、检索排序 | 否 |
| 仓储测试 | 事件追加、乐观并发、归约器语义 | 否 |
| 模型层测试 | 结构化解析、路由、用量记录、数据出境过滤 | 否 |
| 适配层契约测试 | 导入不连库、连接惰性、能力注册表语义 | 否 |
| 案例集测试 | 解析、澄清、字段、规划的期望行为 | 否 |
| 真实数据测试 | Schema 验证、样本验证、端到端闭环 | 是 |
| 浏览器验收 | 关键路径与全界面 | 是 |

纯逻辑与真实数据测试严格分层，保证凭据未就绪时开发仍可推进且验证有效。

### 15.4 质量门禁

代码风格检查、静态类型检查、测试与覆盖率、前端测试与类型检查、前端构建，全部必须通过。**覆盖率缺口出现在状态迁移、级联失效、公式算子、查询规划、点时判断、权限或修复逻辑上时，阻塞发布。**

每个功能点先写可观察行为测试，再实现最小功能，验证通过后单独提交。

## 16. 部署

单机容器编排，三个服务：

| 服务 | 网络 | 密钥 | 端口 |
|---|---|---|---|
| 前端（静态资源 + 反向代理） | 内部网络 | 无 | **唯一暴露的主机端口** |
| 后端 | 内部网络 | Wind + 模型密钥 | 不暴露 |
| Worker | **无网络** | **无** | 无 |

共享命名卷：任务队列、工件目录、元数据库。反向代理需为事件推送路径关闭缓冲。

**部署配置本身要有契约测试** —— 它是安全边界的一部分：断言 Worker 网络模式为 `none`、断言 Worker 环境中不含任何密钥变量。误配置会导致构建失败，而不是在生产上悄悄给 Worker 开一条网络。

不提供高可用集群。

## 17. 里程碑与风险

### 17.1 阶段目标

| 阶段 | 目标 |
|---|---|
| 第 1 周 | 可信基础：凭据整改、工程环境、领域契约、状态机、模型接入、解析与澄清、案例集 |
| 第 2 周 | P0 计算闭环：元数据目录、字段发现、Schema 与样本验证、函数规划、公式编译、manifest 执行、隔离 Worker、三层校验 |
| 第 3 周 | P0 网页稳定与 P1：会话接口与可恢复推送、工作台、确认卡、浏览器验收、文本 PDF、研报抽取 |
| 第 4 周 | P2 原型与交付：OCR、两轮修复、因子检验、因子库、多因子与指数、权限、部署、全量验收与交付文档 |

**硬门槛**：第 2 周末必须跑通真实数据的 P0 闭环。未达成则冻结第 4 周的非必要模块，优先修复 P0。

### 17.2 主要风险

| 风险 | 缓解 |
|---|---|
| 用户确认的公式与实际执行不一致 | 模型只出 AST，后端确定性渲染 canonical 公式供确认（§5.2） |
| 预处理重复执行、顺序错误 | 预处理与公式分离，改为有序流水线（§5.4） |
| 隐性未来函数（信号与交易时点） | 显式时间口径契约 + 保守默认 + 写入计划与工件（§5.5） |
| Wind 字段口径与文档不一致 | WDS 元数据目录 + `information_schema` 验证 + 分形态样本验证（§6） |
| 财务数据点时可得性 | 报告期形状内建基准日约束 + 规划期硬失败 + 公式层校验 |
| 结果无法复现 | 完整工件链 + 输入哈希 + 全量版本号（§9） |
| 任务崩溃滞留 | 租约 + 超时恢复 + 幂等键（§7.4） |
| 内部数据外流 | B4 边界 + 最小发送 + 本地模式 + 审计不留正文（§13.4） |
| 口径无人逐条复核 | 口径登记表 + 量级校验 + 对拍 + 三值状态 + 下游闸门 + 抽样验收证据包（§14） |
| 研报公式识别不稳定 | 明确首期边界 + 置信度不足转人工确认（§10.1） |
| 系统只对现有案例定向通过 | 扩大案例集 + 隐藏验收集 + 量化指标（§15） |

### 17.3 进度压力下的切线顺序

只按此顺序冻结，且不得削弱正确性或安全性：

1. 步骤动画与视觉打磨
2. 管理端界面打磨（保留后端强制的角色校验）
3. OCR 覆盖广度
4. 指数加权模式（保留等权与因子得分加权）
5. 分析图表打磨（保留指标输出）

**绝不削减**：公式确认、字段确认、真实数据、时间口径与公告日处理、manifest 校验、Worker 隔离、结果校验、端到端浏览器验证。

## 附录 A：本版主要修订

相对上一版设计，本版根据评审意见做了以下修订。前九项改变了架构或契约，后四项补充了缺失需求。

| # | 修订 | 性质 |
|---|---|---|
| 1 | 模型不再同时产出展示公式与执行公式；改为**只出 AST，后端确定性渲染 canonical 公式**供用户确认；增加变量绑定、结构复杂度、数值合法性三重校验 | 契约变更 |
| 2 | 预处理与公式**分离**：AST 移除去极值/标准化/行业中性化三个算子（算子由 14 个减为 11 个），预处理改为**有序流水线**并区分变量级与因子级 | 契约变更 |
| 3 | 新增**时间口径契约**（观测时点、信息可得时点、信号日、交易日、执行价格、前向收益起止），定义首期默认口径与保守规则 | 新增契约 |
| 4 | 角色表述修正为"无专职研究人员全程参与，关键节点由带教老师抽样确认"；`disputed` 从警告升级为**阻塞** | 口径治理 |
| 5 | **WDS 正式纳入架构**作为字段元数据与业务口径来源，与 Wind MySQL 取数职责分离；字段发现扩展为七层漏斗 | 架构新增 |
| 6 | 小样本验证按**数据形态**分策略；**Schema 验证与数据存在性验证分离**；返回状态从二值细化为六种 | 功能变更 |
| 7 | 新增**第四条信任边界 B4**（内部数据 → 外部模型），定义默认禁止发送清单、最小发送清单、本地模式与审计要求 | 安全新增 |
| 8 | 任务队列补充**租约、超时恢复、幂等键、取消、工件清理、磁盘告警** | 功能新增 |
| 9 | **Worker 不再执行生成的 Python 源码**，改为直接执行签名校验后的 manifest；生成代码降级为用户导出产物。删除子进程动态执行与源码 AST 白名单等复杂度 | 架构简化 |
| 10 | 补充**修订事件与级联失效规则**；归约器从"最后非空获胜"改为带业务语义；支持版本回退 | 功能新增 |
| 11 | 复现记录扩展到**输入侧**：工件链、输入哈希、查询时点、来源表字段、全量版本号 | 功能新增 |
| 12 | 研报能力边界收窄并写明：只承诺文本型可复制正文；图片公式与扫描件转人工确认；置信度不足不得执行 | 边界澄清 |
| 13 | 案例集扩至 20–30 自然语言 + 5–10 歧义 + 6–10 研报，增设**隐藏验收集**与六组量化指标 | 验收强化 |
