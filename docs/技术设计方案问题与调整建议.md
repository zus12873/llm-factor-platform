# 技术设计方案问题与调整建议

> 本文档整理当前技术设计方案中需要优先调整的问题，以及建议补充的需求。  

---

# 一、必须优先调整的问题

## 1. `formula_text` 与 `formula_ast` 可能不一致

### 当前问题

文档规定：

- `formula_text` 只用于展示；
- `formula_ast` 才是实际执行内容；
- 两者都由大模型返回。

这会形成两个独立的事实来源，存在严重风险：

> 用户可能确认了界面上的公式 A，但系统实际执行的是 `formula_ast` 所表达的公式 B。

即使不是恶意行为，大模型也可能在文本公式和结构化 AST 中出现以下不一致：

- 符号不一致；
- 时间窗口不一致；
- 因子方向不一致；
- 权重不一致；
- 变量名称不一致；
- 算子含义不一致。

在这种情况下，系统虽然满足了代码执行安全要求，但用户确认不再具有真实意义，因为用户确认的并不是系统最终执行的唯一事实来源。

### 建议修改

不要让模型同时生成两个彼此独立、都可能被视为正式公式的内容。

推荐流程：

```text
模型只生成 formula_ast
→ 后端校验 AST
→ 后端根据 AST 确定性渲染 canonical_formula
→ 用户确认 canonical_formula
→ 后续执行同一份 AST
```

其中：

- `formula_ast` 是唯一可执行公式；
- `canonical_formula` 由后端从 AST 确定性生成，是用户确认的正式公式；
- `formula_text` 可以保留，但仅作为自然语言解释；
- `formula_text` 不能作为用户最终确认的正式公式；
- `formula_text` 不参与编译和执行；
- 用户在界面中看到并确认的公式，必须由实际执行的 AST 直接渲染得到。

### 需要增加的校验

#### 变量绑定校验

- AST 中引用的变量必须全部在 `variables` 中定义；
- `variables` 中的逻辑名称不能重复；
- AST 引用了未定义变量时，必须直接阻塞；
- `variables` 中存在未被 AST 使用的变量时，给出警告；
- 变量名称应满足统一命名规范；
- 变量名称映射必须在生成执行计划前完成确认。

#### 结构复杂度校验

- AST 节点数设置上限；
- AST 递归深度设置上限；
- 单个算子的参数数量设置上限；
- 滚动窗口大小设置上限；
- 不允许异常大的时间窗口；
- 不允许空参数或非法参数类型；
- 不允许未登记算子。

#### 数值合法性校验

- 权重必须为有限数；
- 禁止 `NaN`、`inf` 和 `-inf` 作为权重或字面量；
- 多因子权重是否需要归一化，应明确规定；
- 除法分母为零时必须有确定的异常处理；
- 对数输入为非正数时必须有确定的异常处理；
- 溢出、无穷值和非法值必须统一转换为缺失值或阻塞执行；
- 公式方向与 `direction` 字段之间应进行一致性检查。

### 调整后的推荐数据契约

```yaml
factor_spec:
  formula_ast: ...
  canonical_formula: "由后端从 formula_ast 确定性生成"
  formula_explanation: "由大模型生成的自然语言解释，仅用于展示"
```

## 2. 预处理规则存在“双重执行”风险

### 当前问题

文档中同时存在两套预处理表达方式：

#### AST 中的变换算子

- `rank`
- `zscore`
- `winsorize`
- `industry_neutralize`

#### `PreprocessingRules` 中的预处理开关

- 去极值；
- 标准化；
- 行业中性化；
- 其他布尔配置。

这会产生执行歧义，例如：

> 因子 AST 已经执行了一次 `zscore`，全局预处理规则又要求标准化，那么最终应执行一次还是两次？

文档在公式校验中虽然提到了“重复标准化”，但更合理的做法是从数据契约层直接消除双重表达，而不是等到执行后再判断。

此外，使用布尔开关无法表达预处理操作的先后顺序，而因子处理中：

- 先中性化再标准化；
- 先标准化再中性化；

二者的结果并不相同。

### 建议修改

需要在以下两个方案中选择一种，并在整个系统中保持一致。

### 方案 A：推荐方案

#### 设计原则

- 原始数据和因子预处理统一放在 `PreprocessingPipeline`；
- 因子数学公式放在 AST；
- AST 不再允许以下算子：
  - `winsorize`
  - `zscore`
  - `industry_neutralize`

#### 优点

- 数学公式和预处理职责清晰；
- 预处理顺序可以显式表达；
- 可以对变量级处理和因子级处理进行区分；
- 更容易避免重复执行；
- 用户确认公式时不会混入数据清洗逻辑；
- 便于后续扩展不同去极值和中性化方法。

### 方案 B

#### 设计原则

- 所有变换都进入 AST；
- `PreprocessingRules` 只保留数据和股票池相关规则，例如：
  - 股票池过滤；
  - 复权方式；
  - ST 过滤；
  - 停牌过滤；
  - 上市时间过滤；
  - 数据频率；
  - 缺失样本过滤。

#### 优点

- 所有因子计算逻辑都在一棵 AST 中；
- 执行逻辑集中。

#### 缺点

- 用户确认的公式会包含大量预处理节点；
- AST 更复杂；
- 更难区分变量预处理和最终因子预处理；
- 更容易出现重复变换。

### 推荐的数据结构

建议采用方案 A，并将布尔开关改为有顺序的处理流水线：

```yaml
preprocessing:
  - operation: winsorize
    target: variables
    method: mad

  - operation: industry_neutralize
    target: factor

  - operation: zscore
    target: factor
```

每个步骤至少包含：

```yaml
operation: winsorize
target: variables
method: mad
order: 1
parameters:
  n_sigma: 3
```

### 需要明确的语义

- `target=variables`：对原始变量分别处理；
- `target=factor`：对公式计算后的最终因子处理；
- 每个操作必须有明确顺序；
- 不允许同一目标重复执行相同操作，除非用户明确要求；
- 系统应检测重复标准化、重复去极值和重复中性化；
- 预处理流水线也需要版本化和可追溯；
- 用户确认时应展示完整预处理顺序。

## 3. 日频因子的“可用时间”和“交易时间”没有定义完整

### 当前问题

文档已经处理了：

- 报告期；
- 公告日；
- 历史指数成分股；
- 预热窗口；
- 点时数据可得性。

但还没有完整定义：

> T 日收盘价计算出的因子，到底允许用于 T 日收益，还是只能从 T+1 开始？

典型问题包括：

- 使用 T 日收盘价的因子，在 T 日收盘前并不可知；
- 使用 T 日收盘价形成信号，通常最早只能在 T+1 交易；
- 财务公告如果在收盘后发布，不能简单从公告日期当天使用；
- 前向收益口径可能是：
  - T 日收盘到 T+5 日收盘；
  - T+1 日开盘到 T+6 日开盘；
  - T+1 日收盘到 T+6 日收盘；
- 不同交易时点会显著影响因子检验结果。

如果不定义这些字段，系统即使没有读取“未来字段”，仍然可能通过错误的信号和交易时点形成隐性未来函数。

### 建议新增字段

```text
observation_time
information_available_time
signal_date
trade_date
execution_price
forward_return_start
forward_return_end
```

### 字段含义

#### `observation_time`

原始数据的观测时点。

示例：

- T 日收盘价；
- T 日成交额；
- 某财务报告期数据。

#### `information_available_time`

该信息在真实市场中可被研究者获得的时点。

示例：

- T 日收盘后；
- 公告日盘前；
- 公告日盘后；
- 数据正式入库时间。

#### `signal_date`

系统正式形成因子信号的日期。

#### `trade_date`

因子信号允许用于交易或收益观察的最早日期。

#### `execution_price`

默认执行价格，例如：

- 次日开盘价；
- 次日收盘价；
- VWAP；
- 不涉及交易，仅用于未来收益计算。

#### `forward_return_start`

未来收益的起始时点。

#### `forward_return_end`

未来收益的结束时点。

### 首期默认口径

建议明确规定：

> 日频行情因子在 T 日收盘后计算，默认从 T+1 开始观察未来收益；财务数据按实际公告可得日生效。

可进一步细化为：

```yaml
time_convention:
  observation_time: "T_CLOSE"
  information_available_time: "T_AFTER_CLOSE"
  signal_date: "T"
  trade_date: "T+1"
  execution_price: "NEXT_OPEN"
  forward_return_start: "T+1_OPEN"
  forward_return_end: "T+N_OPEN"
```

### 额外要求

- 财务公告需要区分盘前、盘中、盘后；
- 无法获取公告具体时间时，应采用保守规则；
- 默认不得在公告日当日直接使用盘后公告；
- 因子检验页面必须展示收益起止口径；
- 同一实验中的所有因子必须使用一致的时间口径；
- 时间口径应写入执行计划和结果工件；
- 时间口径变化应导致执行计划和结果失效并重新运行。

## 4. “没有额外研究人员”被解释成了“无人做领域确认”

### 当前问题

文档将“没有安排研究人员参与”升级成架构级风险，并建立了：

- `unreviewed`
- `reviewed`
- `disputed`
- 证据包；
- 下游闸门。

这一设计本身比较严谨，但当前实际情况更接近：

> 没有另外安排一名专职研究人员全程参与，主要由开发者完成，关键问题再请带教老师确认。

这并不等于：

- 完全没有领域复核；
- 所有口径都只能由程序自动决定；
- 最终没有任何人进行验收。

开发者本身也承担量化研究工作，带教老师可以在关键节点进行最终抽样确认。

### 建议重新定义角色安排

建议将原文修改为：

> 暂无专职研究人员全程参与；由开发者完成口径整理、证据生成和初步核验，关键指标及最终验收由带教老师进行抽样确认。

### 状态定义

系统仍可保留三值状态，但必须严格区分：

#### `unreviewed`

- 尚未由带教老师确认；
- 可以用于原型测试；
- 可以进行内部试算；
- 不能作为正式发布结果；
- 界面必须明确标记“未复核”。

#### `reviewed`

- 已由带教老师或指定复核人员确认；
- 可以用于正式演示、因子库和后续发布；
- 需要保存复核人、复核时间和复核意见。

#### `disputed`

- 已知字段、公式或业务口径存在问题；
- 禁止执行；
- 禁止发布；
- 禁止进入因子库；
- 禁止进入多因子和指数等下游模块；
- 不允许通过普通用户操作绕过。

### 对已知错误映射的处理

对于以下类型问题：

- “流通市值”映射为“流通股本”；
- “经营活动现金流”映射为“间接法起点净利润”；
- 业务含义与字段含义明显不一致；

应直接标记为 `disputed` 并阻塞，而不是仅发警告。

### 需要保存的复核信息

```yaml
review_status: reviewed
reviewer: "带教老师"
reviewed_at: "2026-08-xx"
review_comment: "确认使用 ROE_TTM 口径"
evidence_version: 3
```

## 5. WDS 没有正式进入系统的数据字典设计

### 当前问题

当前字段检索主要依赖：

- `wind_field_index.md` 中的表名和字段名；
- 32 条人工别名；
- BM25。

文档也承认：

- 字段目录缺少资产类型；
- 缺少数据频率；
- 缺少业务解释；
- 缺少单位；
- 缺少时间口径；
- 因此 BM25 的过滤能力实际不足。

既然老师已经提供 WDS，应将其正式纳入架构。

### 建议明确定位

```text
WDS 是字段元数据和业务口径来源；
Wind MySQL 是实际取数来源。
```

两者职责不同：

- WDS：回答“应该查什么”；
- Wind MySQL：回答“如何取出真实数据”。

### 建议增加 WDS 元数据同步模块

建议新增：

```text
wind/wds_sync.py
wind/metadata_catalog.py
wind/metadata_repository.py
```

模块职责：

1. 从 WDS 整理或导出字段元数据；
2. 将元数据保存到本地结构化目录；
3. 与现有 `wind_field_index.md` 合并；
4. 为字段检索提供更完整的业务信息；
5. 对元数据进行版本管理。

### 建议收集并本地化的内容

- 表中文名；
- 表英文名；
- 字段中文解释；
- 字段英文解释；
- 单位；
- 数据频率；
- 资产类型；
- 主键；
- 关联键；
- 证券代码字段；
- 交易日字段；
- 公告日字段；
- 报告期字段；
- 数据更新时间；
- 更新方式；
- 是否为原始字段；
- 是否为衍生字段；
- 业务备注；
- 数据可得性说明；
- 字段适用范围；
- 是否存在修订版本。

### 运行方式

运行时不必每次实时访问 WDS 网站。

建议流程：

```text
开发阶段访问 WDS
→ 整理并导出元数据
→ 保存到本地字段目录
→ 运行时优先查询本地目录
→ 遇到未覆盖字段时再人工补充
```

### 建议的数据结构

```yaml
table: ashareeodderivativeindicator
field: s_val_mv
table_name_zh: A股日行情估值衍生指标
field_name_zh: 当日总市值
field_name_en: Total Market Value
asset_type: stock
frequency: daily
unit: ten_thousand_cny
code_field: s_info_windcode
observation_date_field: trade_dt
announcement_date_field: null
report_period_field: null

```

### 调整后的字段检索顺序

```text
已有专用函数
→ 人工维护别名
→ WDS 本地元数据目录
→ BM25 / 向量检索
→ information_schema 验证
→ 数据样本验证
→ 用户确认
```

## 6. 小样本验证不能统一采用“3只证券 × 5个交易日”

### 当前问题

统一使用“3只证券 × 5个交易日”只适合日行情类字段，不适用于：

- 季度财务数据；
- 年度数据；
- 公告事件；
- 静态证券属性；
- 历史行业区间；
- 指数成分变化。

例如：

- 财务字段在 5 个交易日内可能没有任何记录；
- 公告事件在短区间内可能为空；
- 指数成分变化需要覆盖调仓日；
- 区间数据需要覆盖进入和退出事件。

如果统一使用短时间窗口，系统可能将“样本区间没有数据”错误判断为“字段无效”。

### 应按数据形态制定采样策略

| 数据类型 | 建议采样              |
| ---- | ----------------- |
| 日频行情 | 3只证券 × 5—20个交易日   |
| 季度财务 | 3只证券 × 8个报告期      |
| 年度数据 | 3只证券 × 5个年度报告期    |
| 公告事件 | 3只证券 × 2—3年       |
| 静态信息 | 10只不同板块证券的截面      |
| 区间数据 | 覆盖至少一次进入和退出事件     |
| 指数成分 | 至少两个历史调仓日         |
| 行业归属 | 至少覆盖一个行业变更或多个历史截面 |
| 基金数据 | 覆盖至少一个完整披露周期      |

### Schema 验证与数据存在性验证应分开

#### Schema 验证

验证：

- 表是否存在；
- 字段是否存在；
- 字段类型；
- 时间字段；
- 代码字段；
- 主键或业务键；
- 字段是否可用于当前查询形状。

#### 数据存在性验证

验证：

- 当前样本区间是否有数据；
- 非空率；
- 重复键；
- 数值范围；
- 单位；
- 时间覆盖；
- 返回行数；
- 样例值。

### 返回状态建议

不要只返回“通过/失败”，建议区分：

```text
SCHEMA_VALID_DATA_PRESENT
SCHEMA_VALID_NO_DATA_IN_SAMPLE
SCHEMA_VALID_DATA_SPARSE
SCHEMA_INVALID
FIELD_INVALID
TIME_ROLE_INVALID
```

对于“Schema 存在但样本为空”，系统应返回：

> 字段存在，但当前样本区间无数据。

而不是将该字段直接判定为错误。

## 7. 外部大模型的数据合规边界缺失

### 当前问题

文档已经设计了：

- 密钥保护；
- SQL安全；
- Worker隔离；
- PDF提示注入防护；
- AST白名单。

但还缺少更现实的数据合规问题：

> 哪些内容可以发送给 Kimi 等外部 API？

系统可能处理：

- 卖方研报；
- Wind字段元数据；
- Wind原始字段值；
- 内部研究想法；
- 公司内部文档；
- 用户上传文件；
- 运行错误和日志。

即使老师建议使用 API，也应明确数据边界。

### 建议增加第四条信任边界

```text
B4：内部数据 → 外部模型服务
```

### 需要明确确认的问题

- 是否允许将完整卖方研报发送到外部模型；
- 是否允许发送 Wind 原始字段值；
- 是否允许发送内部研究想法；
- 是否需要脱敏；
- 服务商是否保留输入内容；
- 是否需要使用公司批准的模型账户；
- 是否允许使用个人 API 账户；
- 哪些内容只能在本地处理；
- 是否需要保留模型调用审计；
- 是否允许日志保存完整正文。

### 建议制定的规则

#### 默认禁止发送

- Wind 原始数据默认不发送给 LLM；
- 数据库连接信息不发送；
- 密钥不发送；
- 内部代码仓库内容不发送；
- 未经授权的内部文档不发送；
- 完整结果数据不发送。

#### 允许发送的最小内容

LLM 仅接收：

- 字段元数据；
- 公式结构；
- 用户明确输入的研究想法；
- 必要的字段说明；
- 经过裁剪和脱敏的研报片段；
- 必要的错误摘要；
- 不含敏感值的结构化上下文。

#### 研报处理

- 上传研报前必须确认授权范围；
- 内部或受版权限制文档不能使用个人 API 账户；
- 优先只发送与因子相关的高分片段；
- 不默认发送完整 PDF；
- 页面原文进入模型前应进行敏感信息扫描；
- 调用日志中不保存完整研报正文。

#### 本地禁用模式

系统应支持：

```text
本地解析，不调用外部模型
```

该模式下：

- PDF只做本地文本提取；
- 字段检索只用本地目录；
- 用户可以手动确认公式；
- 不向外部API发送任何正文。

#### 审计要求

保留：

- 调用时间；
- Provider；
- 模型；
- 输入类型；
- 是否脱敏；
- 文本长度；
- Token数；
- 成本；
- 调用结果；
- 失败原因。

但不默认保存完整敏感正文。

## 8. 文件队列缺少崩溃恢复机制

### 当前问题

当前文件队列通过原子 `rename` 实现任务抢占，可以防止两个 Worker 同时领取同一任务。

但无法处理以下情况：

> Worker 已经将任务从 `pending/` 移到 `running/`，随后进程崩溃，任务会永久停留在 `running/`。

文档明确不使用心跳，但至少需要租约或超时恢复机制。

### 建议增加任务租约

任务目录中的 `job.json` 至少保存：

```text
job_id
session_id
session_version
claimed_by
claimed_at
lease_expires_at
attempt
input_sha256
```

建议补充：

```text
idempotency_key
created_at
started_at
finished_at
cancel_requested
timeout_seconds
max_attempts
artifact_retention_until
```

### 超时恢复流程

```text
扫描 running 任务
→ 判断 lease_expires_at 是否已过期
→ 检查是否已经存在完整结果
→ 有完整结果则转 completed
→ 无结果且 attempt < max_attempts，则重新放回 pending
→ 无结果且达到最大重试次数，则标记 failed
→ 记录恢复事件和失败原因
```

### 需要增加的功能

#### 重复执行幂等键

相同的以下内容应生成同一幂等键：

- `session_id`
- `session_version`
- `manifest_sha256`
- `input_sha256`

重复请求不应生成多个等价任务。

#### 任务取消

- 用户可以请求取消；
- `pending` 任务直接标记取消；
- `running` 任务写入取消标记；
- Worker在安全检查点读取取消状态；
- 取消后不得写入正式结果。

#### 任务超时

- 每个任务设置运行上限；
- 超时后终止；
- 返回结构化错误；
- 是否允许重试由错误分类决定。

#### 工件清理策略

明确以下内容的保存期限：

- 上传PDF；
- 中间文本；
- 输入Parquet；
- 输出Parquet；
- 日志；
- 错误工件；
- 临时文件；
- 生成代码。

#### 磁盘空间告警

- 定期检查可用空间；
- 达到阈值时禁止接收新任务；
- 优先清理过期临时工件；
- 保留不可变正式工件；
- 记录清理日志。

## 9. 当前“生成代码＋执行代码”存在不必要的复杂度

### 当前问题

当前生成代码实际只是固定包装：

```text
嵌入 FactorSpec 和 ExecutionPlan
→ 调用平台内部 run_program()
```

同时：

- Monaco 仅只读展示；
- 用户不能自由修改并执行；
- 真实计算逻辑位于平台内部 runtime；
- 生成的 Python 本身不承担核心业务逻辑。

在这种情况下，Worker 没有必要真正执行一份生成的 Python 源码。

当前设计因此额外引入了：

- Python 子进程执行；
- AST 源码白名单；
- 源码参数解析；
- 动态执行风险；
- “生成代码和实际执行代码是否一致”的证明成本。

### 推荐调整

Worker 直接读取经过签名和校验的 `manifest.json`：

```text
Worker读取经过签名和校验的 manifest
→ 验证 schema、版本和哈希
→ 直接调用 runtime 执行
→ 输出结果
```

### 推荐分成两个产物

#### 内部执行产物

```text
manifest.json
```

内容包括：

- `FactorSpec`
- `ExecutionPlan`
- 预处理流水线；
- 时间口径；
- 字段选择；
- 输入工件哈希；
- 版本；
- 签名；
- 执行参数。

这是平台唯一实际执行的对象。

#### 用户导出产物

```text
factor.py
```

或：

```text
factor.ipynb
```

用途：

- 用户审查；
- 复制；
- 下载；
- 在批准环境中复现；
- 答辩展示。

该代码由同一份 manifest 确定性生成，但不作为内部 Worker 的执行载体。

### 调整后的安全收益

可以删除或简化：

- Python子进程动态执行；
- 大部分源码AST白名单；
- 动态import检查；
- 源码参数解析；
- 一部分沙箱攻击面。

仍应保留：

- Formula AST 校验；
- Manifest Schema 校验；
- 工具白名单；
- 查询范围限制；
- 无密钥 Worker；
- 无网络 Worker；
- 资源限制；
- 输入输出哈希校验。

### 若继续执行生成代码

如果仍坚持让 Worker 执行生成的 Python，技术文档必须明确说明：

- 为什么不能直接执行 manifest；
- 生成代码相比 manifest 直接执行带来的必要收益；
- 如何保证界面展示代码与实际执行代码逐字节一致；
- 如何防止源码在队列中被篡改；
- 如何验证源码哈希；
- 如何处理Python运行时环境漂移。

否则会形成“为了证明安全，先制造一个需要额外安全处理的对象”的不必要复杂度。

## 10. 用户修改和回退流程不完整

### 当前问题

当前状态机主要支持：

- 正常向前推进；
- 执行失败后进入修复。

但真实用户可能会：

- 确认公式后修改公式；
- 确认字段后发现口径错误；
- 修改股票池；
- 修改日期范围；
- 复制当前因子形成新版本；
- 取消执行；
- 使用相同公式重新运行新日期；
- 修改预处理规则；
- 修改调仓频率；
- 修改时间口径。

### 建议增加事件

```text
FORMULA_REVISED
FIELDS_REVISED
REQUEST_REVISED
EXECUTION_CANCELLED
SESSION_CLONED
RERUN_REQUESTED
```

建议进一步增加：

```text
PREPROCESSING_REVISED
TIME_CONVENTION_REVISED
UNIVERSE_REVISED
DATE_RANGE_REVISED
```

### 下游失效规则

上游修改后，必须使所有依赖该内容的下游产物失效。

#### 公式变化

```text
公式变化
→ 清空字段选择
→ 清空执行计划
→ 清空生成代码
→ 清空输入工件
→ 清空执行结果
→ 清空校验结果
```

#### 字段变化

```text
字段变化
→ 清空执行计划
→ 清空生成代码
→ 清空输入工件
→ 清空执行结果
→ 清空校验结果
```

#### 日期范围变化

```text
日期变化
→ 清空执行计划
→ 清空输入数据
→ 清空执行结果
→ 清空校验结果
```

#### 股票池变化

```text
股票池变化
→ 清空字段样本验证
→ 清空执行计划
→ 清空输入数据
→ 清空执行结果
```

#### 预处理变化

```text
预处理变化
→ 清空代码或 manifest
→ 清空执行结果
→ 清空校验结果
```

#### 时间口径变化

```text
时间口径变化
→ 清空执行计划
→ 清空未来收益定义
→ 清空执行结果
→ 清空因子检验结果
```

### Reducer 调整

当前快照采用“最后一个非空值获胜”，可能出现旧产物残留，例如：

> 新公式已经确认，但快照中仍然保留旧字段、旧 ExecutionPlan 和旧代码。

因此应使用具有业务语义的 Reducer，而不是简单覆盖。

Reducer需要显式处理：

- 哪些事件写入新值；
- 哪些事件使旧值失效；
- 哪些事件清空下游数据；
- 哪些旧工件保留为历史版本；
- 当前版本使用哪些工件。

### 版本管理

- 每次修改形成新版本；
- 历史版本不可覆盖；
- 可以查看版本差异；
- 可以回退到历史版本；
- 回退后重新生成下游工件；
- 不直接复用已经失效的旧结果。

source_fields

## 12. 研报公式抽取的能力边界还需更明确

### 当前问题

文档已经覆盖：

- 文本型PDF；
- 页码证据；
- 提示注入处理；
- 中文和英文研报。

但卖方研报中的公式可能出现在：

- 图片；
- 多栏排版；
- 表格；
- 上下标；
- 希腊字母；
- 公式截图；
- 页眉页脚；
- 脚注；
- 跨页公式；
- 扫描页面。

普通OCR对数学公式的识别并不稳定。

如果P1阶段笼统承诺“根据研报识别因子公式”，现场验收可能遇到公式全部为图片或复杂数学排版的研报，从而造成预期不一致。

### 建议明确首期验收边界

建议写成：

> 首期支持正文中可复制、变量定义明确的中英文文本型研报；图片公式、复杂数学排版和扫描版研报仅识别正文提示，并要求人工确认公式。

### 首期支持

- 可复制正文文本；
- 公式以普通文本或可解析字符存在；
- 变量定义明确；
- 因子口径在正文中有说明；
- 可定位页码；
- 中文和英文文本；
- 简单表格旁的变量说明。

### 首期不承诺自动准确识别

- 纯图片公式；
- 复杂LaTeX排版；
- 多层上下标；
- 大量希腊字母；
- 扫描版PDF；
- 跨页公式；
- 复杂多栏错序；
- 公式截图；
- 表格中高度压缩的公式。

### 处理方式

对于无法可靠识别的公式：

```text
识别到可能存在因子公式
→ 提取附近正文和页码
→ 标记“公式需人工确认”
→ 允许用户手动输入或修改公式
→ 再转换为 Formula AST
```

系统不得在公式识别置信度不足时直接进入执行。

### 建议增加置信度和状态

```yaml
formula_extraction:
  status: needs_manual_confirmation
  confidence: 0.62
  source_pages: [12, 13]
  extracted_text: "..."
  warning: "公式包含图片和上下标，自动识别可能不准确"
```
