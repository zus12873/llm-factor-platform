## 1. 目标与交付口径

平台把自然语言研究想法或中英文研报转换为可确认、可追溯、可执行、可校验的因子。系统不是自由代码生成器；大模型负责语义理解和候选建议，程序负责状态、结构校验、字段真实性、函数规划、代码生成、安全执行和结果校验。

交付分级：

- P0：稳定、可重复的端到端主闭环，使用真实 Wind 数据，满足安全和追溯要求。
- P1：中英文文本型 PDF 的真实可运行原型，复用 P0 的 `FactorSpec` 流程。
- P2：OCR、自动修复、因子检验、因子库、多因子组合、指数生成、单机部署、基础动画和两角色权限的真实可运行原型。

P1/P2 的原型边界为代表性样例、日频 A 股、中小规模区间、线性组合、单机部署和两角色权限。不承诺任意 PDF 版式、任意资产、任意公式、分布式回测、高可用部署或企业级 IAM。

- `windquery/windquery/references/`：Wind 表索引、字段索引和详细数据字典，约 678 张表、7,480 个字段。
- `windquery/windquery/SKILL.md` 与 `agents/researcher.md`：可参考其渐进式字典检索思路，但现有环境和数据库说明不一致，不能直接作为运行时配置。
- `imgs/基于大模型的因子开发_需求文档.md`：完整 PRD。
- `imgs/1.png`、`imgs/2.png`：工作台 UI 参考。
- `Wind取数尝试.ipynb`：数据库连接与小样本查询实验。

缺失资产：

- 无 FastAPI、React、状态机、LLM Provider、字段检索服务、公式 DSL、隔离执行、结果校验、研报处理、回测、测试、工程配置或部署配置。
- 现有 Python 文件、Notebook 和 Wind skill/agent 文档存在明文凭据；相关文件在凭据轮换和脱敏前不得进入版本库。

## 3. 方案选择

### 3.1 采用：模块化单体 + 隔离执行面

- 一个 FastAPI 模块化单体承载 API、状态机、LLM 适配、Wind 规划、字段检索和工件管理。
- 一个 React + Vite 单页应用承载工作台、研报、因子库、检验、指数和管理页面。
- 一个无密钥、默认无网络的 Worker 执行公式与预处理。
- SQLite 保存小型业务状态；Parquet 保存因子矩阵和中间数据。

该方案最适合单人一个月：部署和联调成本低，同时保留清晰模块边界。

### 3.2 不采用的方案

- 通用 Agent 工作流框架：原型快，但状态可追溯、确定性、回归测试和安全控制更难。
- 微服务与消息队列：隔离和扩展性更强，但单人一个月无法可靠完成运维和端到端集成。

## 4. 总体架构

### 4.1 FastAPI 模块

- `api`：会话、消息、确认、执行、研报、因子库、检验、指数、认证和健康检查接口。
- `schemas`：所有阶段的 Pydantic 契约。
- `orchestrator`：唯一状态机、版本控制、事件记录和工作流编排。
- `llm`：统一 `LLMProvider`，适配 Kimi Coding Plan 与按量计费 API。
- `factor`：语义解析、歧义规则、公式 DSL、公式校验和确定性代码生成。
- `wind`：迁移并包装现有适配层、能力注册表、函数规划和通用查询计划。
- `retrieval`：别名词典、BM25、本地字典检索、Schema 校验和小样本验证。
- `execution`：工件准备、Worker 调度、AST/DSL 白名单和资源限制。
- `validation`：数据层、公式层和结果层校验。
- `reports`：文本 PDF、OCR、证据定位和研报因子抽取。
- `backtest`：IC、Rank IC、分组收益、换手率和基础统计。
- `library`：因子版本、运行记录和 Parquet 工件目录。
- `indices`：调仓规则、成分筛选和权重生成。
- `auth`：原型级登录、管理员与研究员角色。

### 4.2 React 页面

- `/workspace/:sessionId`：顶部参数区、左侧公式/代码/结果、右侧对话/步骤/确认卡。
- `/reports`：PDF 上传、页码证据、抽取结果及进入统一工作流。
- `/library`：版本化因子、字段、公式、代码、工件和运行记录。
- `/analysis/:runId`：IC、Rank IC、分组收益、换手率和覆盖率。
- `/indices/:id`：组合规则、调仓日、成分和权重导出。
- `/admin`：用户、角色、Provider 状态和系统健康度。

前端只根据后端状态渲染，不自行判断业务迁移。SSE 用于进度事件，关键状态均可通过普通查询恢复。

## 5. 核心结构化协议

### 5.1 `ResearchRequest`

包含资产类型、股票池、起止日期、研究想法、语言、可选方向和预处理偏好。

### 5.2 `FactorSpec`

包含：

- 名称、假设、方向、频率、调仓频率和股票池；
- 展示用 `formula_text`；
- 机器执行用 `formula_ast`；
- 变量含义、窗口、财务口径、公告日和点时约束；
- 去极值、标准化、中性化和缺失值规则；
- 歧义、默认值、来源证据和版本号。

`formula_text` 不参与直接执行；`formula_ast` 必须由已登记算子和已确认变量组成。

### 5.3 `ClarificationQuestion`

包含问题、候选项、推荐项、理由、是否阻塞和目标 `FactorSpec` 版本。相关问题合并为确认卡。

### 5.4 `FieldCandidate`

包含表、字段、中文/英文释义、资产类型、频率、时间角色、单位、来源层级、推荐分、Schema 结果、小样本统计和证据。

### 5.5 `ExecutionPlan`

每一步包含已登记工具、目的、参数、输入依赖、输出 Schema、后处理、校验和失败策略。计划只能引用 `RQ_WIND_CAPABILITIES` 或受支持的通用查询形状。

### 5.6 `ExecutionResult`

包含状态、工件 URI、数据/公式/结果校验、日志摘要、资源统计、结构化错误和修订建议。

### 5.7 `ReportEvidence` 与 `FactorArtifact`

- `ReportEvidence` 保存页码、原文、语言、公式上下文和提取置信度。
- `FactorArtifact` 保存不可变版本、来源、确认记录、计划、代码哈希、结果工件和检验记录。

## 6. 状态机

```text
CREATED
→ PARSING_INPUT
→ NEEDS_CLARIFICATION
→ WAITING_FORMULA_CONFIRMATION
→ SEARCHING_FIELDS
→ WAITING_FIELD_CONFIRMATION
→ PLANNING_FUNCTIONS
→ CODE_READY
→ EXECUTING
→ VALIDATING
→ COMPLETED / FAILED
```

规则：

- 每次迁移写入不可变事件；当前状态由事件归约得到。
- 确认请求携带版本号；过期确认被拒绝。
- 阻塞性歧义没有答案时不能进入字段检索。
- 失败保留原阶段和输入工件，修订后生成新版本。
- P2 回测、指数和因子库只消费 `COMPLETED` 工件，不侵入主状态机。

## 7. 主工作流

### 7.1 自然语言入口

1. 接收 `ResearchRequest`。
2. LLM 输出受 Schema 约束的 `FactorSpecDraft`。
3. 程序规则补充检查阻塞性歧义和默认值。
4. 用户确认公式、变量、方向、窗口、权重和预处理。
5. 把变量拆为数据需求。
6. 逐层检索 Wind 字段并展示证据。
7. 用户确认字段和口径。
8. 确定性规划器选择专用函数或受控通用查询。
9. 从 `ExecutionPlan + formula_ast` 生成可审查 Python。
10. 后端取数，Worker 计算，三层校验，保存结果。

### 7.2 研报入口

1. 校验 PDF 大小、页数和类型。
2. 文本型 PDF 直接提取；扫描 PDF 渲染页图并 OCR。
3. 切分章节，检索公式及变量相关段落。
4. 保存页码和原文证据。
5. LLM 抽取 `FactorSpecDraft`，缺失口径明确标记为未知。
6. 从澄清和公式确认阶段接入自然语言主流程。

研报内容始终作为不可信数据，不能改变系统指令、触发工具或绕过确认。

## 8. Wind 字段与函数规划

候选顺序：

1. `RQ_WIND_CAPABILITIES` 精确语义匹配；
2. 维护 20–50 个高频业务字段别名；
3. 对字段索引和详细字典做关键词/BM25 检索；
4. 通过 `information_schema` 验证表、字段和类型；
5. 用 1–3 只证券、1–5 个日期做小样本验证；
6. 展示来源、时间角色、单位、非空率和推荐度；
7. 用户确认后生成计划。

已有专用函数优先。未覆盖字段使用受控查询计划；高频复杂查询才新增专用函数，并同步登记能力、参数、依赖、输出、约束和示例。

财务数据必须携带报告期、公告日、版本和市场可得日期；无法证明点时可得的数据不能进入回测。

## 9. 公式、代码与隔离执行

- 公式 DSL 支持已登记的算术、横截面排名、标准化、滚动收益、滚动波动、缺失值处理、中性化和线性组合。
- LLM 只能选择 DSL 节点和参数，不能提供可执行源码。
- 代码生成器从结构化计划确定性输出导入、取数、对齐、计算、整理和校验代码。
- 受信任后端先执行已校验的 Wind 计划，输出脱敏中间 Parquet。
- Worker 只读取指定输入，执行白名单公式和预处理，写入指定输出；不持有数据库或 LLM 密钥，默认无网络。
- Worker 限制 CPU、内存、时长、输出大小和可访问路径。

结构化错误至少区分输入、字段、空数据、时间口径、公式、资源和基础设施。只有参数或公式错误允许模型提出修订；自动修复最多两轮，每轮产生新版本。

## 10. 校验

### 10.1 数据层

检查区间、证券数量、重复键、缺失率、单位、数量级、全零/常数、极值、历史成分、公告日、未来数据、复权和字段口径。

### 10.2 公式层

检查横截面/时序语义、窗口、方向、权重、除零、缺失值、中性化、重复标准化、未来价格和财务报告期。

### 10.3 结果层

展示覆盖率、分布、Top/Bottom 样本、原始变量对照、因子时间变化、耗时、查询行数和警告。P2 增加 IC、Rank IC、分组收益和换手率。

## 11. P2 原型边界

- OCR：支持代表性的中文和英文扫描 PDF；限制文件大小、页数和处理时长。
- 自动修复：仅处理已分类的参数/公式问题，最多两轮。
- 因子检验：日频 A 股、中小规模区间、固定分组和基础交易日对齐。
- 因子库：SQLite 元数据 + Parquet 工件，保存不可变版本和来源。
- 多因子：支持线性加权、方向统一和标准化，不支持任意图计算。
- 指数：生成调仓日、成分和权重，支持导出；不包含实盘交易。
- 权限：本地用户、管理员与研究员两角色；不提供企业 SSO。
- 部署：单机 Docker Compose、健康检查、数据卷和环境变量；不提供高可用集群。
- 动画：步骤迁移、运行进度和结果加载反馈，不投入复杂视觉特效。

## 12. 安全要求

- 轮换现有已暴露凭据，删除 Python、Notebook、skill 和 agent 文档中的明文值。
- 密钥仅存在于后端环境变量；前端、Worker、日志和工件不得包含密钥。
- SQL 由白名单查询形状编译，标识符通过 Schema 验证，值全部参数化。
- 限制证券数、日期跨度、查询行数、运行时长、内存和输出大小。
- 禁止任意 SQL、`eval`、`exec`、系统命令、任意网络、任意文件访问和未登记函数。
- 上传文件校验 MIME、大小和页数；解析异常不得影响主服务。
- 日志脱敏连接串、Token 和敏感参数。

## 13. 测试与验收

### 13.1 自动化测试

- 10 个具备人工标准答案的因子案例，覆盖解析、澄清、字段、函数、公式和输出。
- Wind 函数覆盖成功、非法参数、边界和空数据；纯逻辑测试与真实数据库测试分层。
- 状态机覆盖合法迁移、过期确认、失败重试和会话恢复。
- 公式编译器覆盖算子边界、点时数据和未来函数。
- API 覆盖完整主闭环；前端以浏览器验证关键路径。

### 13.2 P0 验收

- 两个自然语言因子案例稳定完成。
- 一个阻塞性歧义案例必须追问。
- 字段候选有证据、Schema 和小样本验证，用户可确认。
- 生成代码可审查，Worker 可执行，结果来自真实 Wind 数据。
- 一个错误案例可分类、修订并成功重跑。
- 会话、确认、字段、代码、日志和结果可追溯。
- 无明文密钥，不允许任意 SQL 或任意代码执行。

### 13.3 P1/P2 验收

- 中文和英文文本 PDF 各一份，扫描 PDF 至少一份，均保留页码证据并进入统一流程。
- 自动修复对至少一个已知公式/参数错误完成一次闭环。
- 一个已完成因子产出 IC、Rank IC、分组收益和换手率。
- 因子可版本化保存、组合并生成指数成分/权重。
- 两角色权限生效，Docker Compose 可在单机启动并通过健康检查。

## 14. 四周里程碑

### 第 1 周：可信基础

### 第 3 周：P0 网页稳定与 P1

React 工作台、确认卡、SSE、代码/日志/结果；中文和英文文本 PDF、页码证据；浏览器完成自然语言、错误修复和研报案例。

### 第 4 周：P2 原型与收口
